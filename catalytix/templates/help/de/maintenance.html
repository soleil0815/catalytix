Updates und Notfallbefehle laufen auf dem Server, im Ordner mit der docker-compose.yml. Eigene Werte (Port, Zeitzone …) stehen in .env; sie wird bei Updates nie überschrieben, ebenso wenig ./data und docker-compose.override.yml.

Das Programm steckt komplett im Image ghcr.io/soleil0815/catalytix. Auf dem Server liegen nur docker-compose.yml, .env und ./data (dazu optional update.sh).

Update: mit einer Container-Verwaltung (Dockhand, Watchtower …) – am besten nachts – oder von Hand mit docker compose pull && docker compose up -d. Oder mit update.sh:

./update.sh                        # neueste Version (oder die in der .env festgelegte)
./update.sh --version=X.Y.Z        # genau diese Version (auch ein Sicherheitsupdate X.Y.Z-s2)
./update.sh --version=latest       # wieder jeder neuen Version folgen
./update.sh --load DATEI.tar.gz    # ohne Internet: Image-Datei aus dem Release
./update.sh --cleanup              # Installationen vor 3.0.0: alte Programmdateien wegräumen

update.sh merkt sich das laufende Image als previous, holt das neue, startet es und wartet auf den Gesundheitscheck. Startet die neue Version nicht, spielt es die Sicherung von vor dem Update zurück und startet wieder die vorige Version (mit Nachfrage, mit -y automatisch). Bringt das Image eine neuere docker-compose.yml mit, legt es sie ab und behält die alte als docker-compose.yml.alt.

Bei jedem Versionswechsel sichert das Programm die Datenbank beim Start selbst (Datensicherung: „vor Update auf X.Y.Z“), bevor es sie anpasst. Eine ältere Version startet nicht auf einer Datenbank, die schon eine neuere benutzt hat – das Protokoll nennt dann die Sicherung, die zurückzuspielen ist. Zurückgehen zu einer älteren Version: ./update.sh --version=X.Y.Z (spielt die passende Sicherung zurück; alles seitdem Eingetragene geht verloren). Eine Version festlegen: CATALYTIX_TAG=X.Y.Z in der .env.

Zeigt die Übersicht den Hinweis, die docker-compose.yml sei veraltet: einmal ./update.sh ausführen oder die Datei aus dem Release ersetzen und docker compose up -d.

Feste Versionen und Sicherheitsupdates: Basis-Image (mit Prüfsumme), Betriebssystem-Pakete und alle Python-Pakete (mit Prüfsummen) sind auf exakte Versionen festgelegt – jeder Bau ergibt dasselbe Image. Auf GitHub werden diese Versionen einmal im Monat am Patchday (zweiter Dienstag) automatisch erneuert, aber nur innerhalb des Unterbaus (Debian 13, Python 3.13, jedes Paket innerhalb seiner Hauptversion). Das neue Image wird ohne Zwischenspeicher gebaut, im fertigen Image getestet und auf Schwachstellen geprüft; nur wenn alles besteht, erscheint es als latest und als <Version>-s<Zähler> (gleiches Programm, nur neue Pakete), mit einem Eintrag im CHANGELOG. Folgt der Server latest (Standard), holt eine Container-Verwaltung, docker compose pull oder ./update.sh diese Sicherheitsupdates. Zusätzlich wird das veröffentlichte Image täglich geprüft, und wöchentlich, wie lange Debian und Python noch Sicherheitsupdates bekommen.

Wenn ein Lauf auf GitHub rot wird (GitHub schickt dann eine E-Mail): Es wurde nichts veröffentlicht, der Server läuft unverändert weiter. Die Ursache steht oben am Lauf. Meist ist eine Korrektur noch keine 7 Tage alt – dann den nächsten Patchday abwarten oder unter Actions → Security update → Run workflow mit cooldown_days = 0 starten. Bei fehlgeschlagenen Tests, Schwachstellen ohne Korrektur im Unterbau oder einer Warnung zum Unterbau ist eine bewusste Änderung nötig; die README beschreibt jeden Fall.

Befehle für den Notfall – jeweils mit docker compose exec catalytix docker-entrypoint.sh davor (über den Entrypoint laufen sie wie die App ohne Root-Rechte, z. B. gehören Sicherungen dann nicht root):

  • flask --app wsgi reset-password admin – neues Passwort für ein lokales Konto (aktiviert es auch wieder und hebt eine Anmeldesperre auf)
  • flask --app wsgi reset-2fa admin – zweiten Faktor zurücksetzen (hebt auch die Sperre nach zu vielen falschen Codes auf)
  • flask --app wsgi create-admin notfall – zusätzliches lokales Admin-Konto
  • flask --app wsgi backup / list-backups – sichern bzw. Sicherungen anzeigen
  • flask --app wsgi restore-for-version X.Y.Z – Sicherung für den Weg zurück zu X.Y.Z einspielen (Server vorher anhalten, mit docker compose run --rm -e CATALYTIX_SKIP_DB_CHECK=1 catalytix davor)
  • flask --app wsgi send-reminders – Erinnerungen jetzt versenden
  • flask --app wsgi apply-retention – Aufbewahrungsfrist jetzt anwenden

Fast alles davon geht auch in der Oberfläche: 2FA zurücksetzen und Anmeldesperre aufheben im Benutzerkonto, Jetzt sichern, Jetzt versenden, Jetzt bereinigen. Die Version steht unten in der Seitenleiste; ein Klick darauf zeigt Lizenz und Quellcode.
