This installation does not use an SQLite database, so the built-in backup is not available. Back up the database with the database server's tools (e.g. mysqldump or pg_dump) and also the ./data folder.

{% else %}

Under Administration → Backup the database is {% if f.backup_enabled %}backed up automatically every day from {{ "%02d"|format(f.backup_hour) }}:00{% else %}currently not backed up automatically – switch on Back up automatically every day{% endif %}. This runs while the library is in use, and every backup is checked for corruption. {% if f.backup_keep == 1 %}Only the newest backup is kept{% else %}The newest {{ f.backup_keep }} are kept{% endif %} (adjustable 1–100); older ones are deleted.

{% endif %}
  • Back up now creates a backup immediately – useful before major changes or an update.
  • Each backup can be downloaded or deleted. Location: ./data/backups or the folder set in CATALYTIX_BACKUP_DIR (e.g. a NAS).
  • If a backup fails, a warning sign appears next to the menu item and administrators get an email{% if not f.mail_on %} (once email delivery is active){% endif %}.
  • The database is backed up. Covers, logo and secret_key are files in ./data – take the whole folder when moving servers. Always restore a database together with its secret_key: without the matching key, 2FA sign-ins and stored SMTP/AD passwords do not work, and Catalytix will not start.

Important: backups are stored on the same server and do not protect against disk failure. Copy the folder to another place regularly.

Restoring (on the server; the current state is backed up automatically first):

docker compose stop catalytix
docker compose run --rm catalytix flask --app wsgi list-backups
docker compose run --rm catalytix flask --app wsgi restore-backup FILENAME.db
docker compose start catalytix

Anything that happened after the backup was taken is lost.
