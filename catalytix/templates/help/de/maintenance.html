Updates und Notfallbefehle laufen auf dem Server, im Ordner mit der docker-compose.yml. Eigene Werte (Port, Zeitzone …) stehen in .env; sie wird bei Updates nie überschrieben, ebenso wenig ./data und docker-compose.override.yml.

Update mit update.sh:

./update.sh --pull                 # neueste Version von GitHub (fertiges Image)
./update.sh --pull=X.Y.Z           # genau diese Version von GitHub
./update.sh --pull=X.Y.Z-s2        # genau dieses Sicherheitsupdate
./update.sh catalytix-X.Y.Z.zip    # klassisch: Paket einspielen und lokal bauen
./update.sh                        # aktuellen Stand neu bauen bzw. neu holen und starten

Mit --pull holt das Skript das von GitHub gebaute Image (ghcr.io/soleil0815/catalytix) samt passender docker-compose.yml und merkt es sich in der .env; ein Zip-Paket schaltet wieder auf lokales Bauen um.

Das Skript prüft das Paket, legt eine Datensicherung an, tauscht erst dann die Programmdateien aus (bei einem Fehler werden die bisherigen wiederhergestellt), baut das Image catalytix:VERSION (schlägt das fehl, läuft der alte Container weiter), startet neu, wartet, bis der Container gesund ist, und räumt danach auf (ältere Images und Zip-Pakete – das vorige bleibt für den Weg zurück –, alte Arbeitsordner). Optionen: --no-backup, --no-cache, --prune (nur der aktuelle Stand bleibt), --no-cleanup (nicht aufräumen), -y (keine Rückfragen), --help. Nötig sind Docker Compose (docker compose oder das ältere docker-compose ab 1.27) und unzip, ersatzweise python3. Die Datenbank wird beim Start automatisch angepasst.

Feste Versionen und Sicherheitsupdates: Basis-Image (mit Prüfsumme), Betriebssystem-Pakete und alle Python-Pakete (mit Prüfsummen) sind auf exakte Versionen festgelegt – jeder Bau ergibt dasselbe Image. Auf GitHub werden diese Versionen jeden Montag automatisch erneuert, aber nur innerhalb des Unterbaus (Debian 13, Python 3.13, jedes Paket innerhalb seiner Hauptversion). Das neue Image wird ohne Zwischenspeicher gebaut, im fertigen Image getestet und auf Schwachstellen geprüft; nur wenn alles besteht, erscheint es als latest und als <Version>-s<Zähler> (gleiches Programm, nur neue Pakete), mit einem Eintrag im CHANGELOG. Folgt der Server latest (Standard nach ./update.sh --pull), holt ein Update mit ./update.sh oder eine Container-Verwaltung diese Sicherheitsupdates. Zusätzlich wird das veröffentlichte Image täglich geprüft, und wöchentlich, wie lange Debian und Python noch Sicherheitsupdates bekommen.

Wenn ein Lauf auf GitHub rot wird (GitHub schickt dann eine E-Mail): Es wurde nichts veröffentlicht, der Server läuft unverändert weiter. Die Ursache steht oben am Lauf. Meist ist eine Korrektur noch keine 7 Tage alt – dann den nächsten Montag abwarten oder unter Actions → Security update → Run workflow mit cooldown_days = 0 starten. Bei fehlgeschlagenen Tests, Schwachstellen ohne Korrektur im Unterbau oder einer Warnung zum Unterbau ist eine bewusste Änderung nötig; die README beschreibt jeden Fall.

Befehle für den Notfall – jeweils mit docker compose exec catalytix docker-entrypoint.sh davor (über den Entrypoint laufen sie wie die App ohne Root-Rechte, z. B. gehören Sicherungen dann nicht root):

  • flask --app wsgi reset-password admin – neues Passwort für ein lokales Konto (aktiviert es auch wieder)
  • flask --app wsgi reset-2fa admin – zweiten Faktor zurücksetzen
  • flask --app wsgi create-admin notfall – zusätzliches lokales Admin-Konto
  • flask --app wsgi backup / list-backups – sichern bzw. Sicherungen anzeigen
  • flask --app wsgi send-reminders – Erinnerungen jetzt versenden
  • flask --app wsgi apply-retention – Aufbewahrungsfrist jetzt anwenden

Fast alles davon geht auch in der Oberfläche: 2FA zurücksetzen und Anmeldesperre aufheben im Benutzerkonto, Jetzt sichern, Jetzt versenden, Jetzt bereinigen. Die Version steht unten in der Seitenleiste; ein Klick darauf zeigt Lizenz und Quellcode.
